# MySQL Schema Documentation

**Project:** 21CTA  
**Purpose:** Proposed logical schema and conventions for a single multi-school MySQL platform  
**Status:** Design reference; not executable DDL and not applied to any database  
**Date:** 2026-11-08

## 1. Database conventions

- MySQL 8.0.16+ (for enforced `CHECK` constraints), InnoDB, `utf8mb4`, strict SQL mode, and UTC connection/session time zone.
- Use explicit migrations tracked in `schema_migrations`; no schema creation or repair by application startup.
- Primary IDs are generated by the backend as UUIDs. Start with `CHAR(36)` under ASCII/binary collation for compatibility with existing UUID APIs. Preserve legacy source IDs in a separate mapping table.
- Use `DECIMAL`, not floating-point types, for marks, percentages, weights and other values where exact arithmetic matters. Specify precision and rounding behavior from existing business rules.
- Store instants as UTC `DATETIME(6)`; expose ISO-8601 timestamps with timezone information from the API.
- Use `JSON` only for genuinely document-shaped content or opaque AI payloads; use normalized rows for entities, permissions and relationships.
- Add indexes for every FK and common tenant/query prefix. Build constraints from observed data and validate duplicates/orphans before enabling them.
- Every school-owned row has a non-null `school_id`. Global reference/catalog rows are explicitly marked global and are not used to store school-specific settings or records.

## 2. Core identity, tenancy and authorization

| Table | Responsibility and key constraints |
|---|---|
| `schools` | Canonical school record; unique stable school code; lifecycle status and audit timestamps. |
| `users` | One central person/profile per identity; unique normalized login identifier(s), status, email/phone verification state. Avoid embedding school role in this row. |
| `auth_credentials` | User FK; password hash and algorithm metadata, changed timestamp, must-reset flag. Restrict access to auth service; never return hashes from API. |
| `auth_sessions` | User FK, hash of refresh/session secret, expiry, rotation/revocation metadata, device metadata as policy allows. Index user and expiry. Store no bearer secret in plaintext. |
| `password_reset_tokens` | User FK, token hash, expiry, consumed timestamp; unique token hash, short TTL and one-time use. |
| `user_mfa_factors` | Optional user FK, factor type, encrypted secret/reference, confirmed/revoked timestamps; encryption keys held outside the database. |
| `roles`, `permissions` | Stable role/permission codes; distinguish platform from school scope. Unique codes. |
| `role_permissions` | Composite PK `(role_id, permission_id)` and restrictive FKs. |
| `school_memberships` | User + school + role + status; unique active assignment policy per `(school_id, user_id, role_id)` or approved membership model; indexed by `(user_id, status)` and `(school_id, status, role_id)`. |
| `school_invitations` | School/role/email, hashed single-use token, expiry, inviter, accepted/revoked state; never store the raw invite token. |
| `parent_student_links` | School-scoped guardian-to-student relationship, verification evidence/status, unique active link; access is limited to linked students. |
| `identity_links` | Source system/table/source ID to central user/profile; unique source identity; link method, evidence, approval actor, status and timestamps. |
| `legacy_id_map` | Unique `(source_system, source_table, source_id)`; stores target table/id, migration status and source checksum. Do not overload user identity links for non-user records. |
| `audit_logs` | Append-only actor, school, action, entity type/id, request/correlation ID, timestamp and redacted before/after detail. Index `(school_id, created_at)` and actor/time. Restrict updates/deletes. |

The super administrator is a platform-scoped role, not a special school membership. School administrators, headteachers, DOS, teachers, students and parents receive school-scoped memberships and permission sets. Role assignment is server-controlled and audited.

## 3. Academic and lesson-planning domains

| Domain | Proposed tables and important relations |
|---|---|
| Staff and learners | `teachers` and `students` reference `schools`; optional user FK; preserve source codes and profile attributes. `parent_student_links` associates verified guardians. |
| Curriculum | `education_levels` (global where appropriate), `subjects`, `classes`, `class_subjects`, `teacher_assignments`; use `school_id` and same-school composite FKs for tenant-owned links. |
| Academic calendar | `academic_years` unique by `(school_id, name)`; `terms` reference same-school year; enforce at most one current year per school using a tested MySQL-compatible uniqueness strategy. |
| Marks and records | `assessment_types`, `assessments`, `marks`, `grading_scales`, `performance_comments`; `marks` unique by `(school_id, assessment_id, student_id)`, with exact numeric types and original/normalized values retained. |
| Lesson planning | Preserve/extend `syllabuses`, `syllabus_units`, `syllabus_lessons`, `units`, `lessons`, `lesson_plans`, plan versions/history, `lesson_materials`, and `special_needs_learners`. Migrate existing System A records without changing legacy IDs. |
| Materials and library | Unified metadata tables for resources/materials, ownership, visibility, subject/class/year/term, file key and checksum; optional AI chunks/usage. File bytes remain in a separate object store until a separately approved migration. |
| Exams and assessments | `examinations`, `examination_classes`, `exam_questions`, `question_bank`, `exam_attempts`, `student_answers`; preserve attempt lifecycle and enforce school ownership through FKs. Guest attempts require separate rate limits and data-retention controls. |

Where existing application code depends on legacy table names or shapes, use repositories/views during transition rather than destructive table renames. Do not create two writable sources of truth for the same domain.

## 4. Remaining school modules

| Module | Proposed relational entities |
|---|---|
| Attendance | `attendance_sessions` (school, class, date, term, recorder, status) and `attendance_entries` (session, student, attendance code, note); unique student per session and audited edits. |
| Timetable | `timetables`, `timetable_entries` (class/teacher/subject/room/time), publication/version metadata; validate teacher/class period conflicts transactionally. |
| Digital class diary | `class_diary_entries` linked to class, teacher, date, lesson/plan where applicable; reflections and review state. |
| Teacher CPD | `cpd_activities`, `teacher_cpd_records`, evidence references and approval state; protect personal/professional data. |
| Notifications | `notifications`, `notification_recipients` or user-owned rows, delivery attempts/outbox; idempotency key and delivery status. |
| AI assistant | `ai_conversations`, `ai_messages` or existing chat equivalents, `ai_usage_events`, provider/model metadata and quotas; minimize or redact prompt content under retention policy. |
| Analytics | Prefer derived queries/materialized aggregate tables with source period, school, metric and refresh time. Never use an aggregate to bypass source authorization. |
| Settings | `platform_settings` for platform scope and `school_settings` with unique `school_id`; secret values live in a secret manager, not settings rows. |

## 5. Tenant integrity and index patterns

- For each school-owned parent table, expose a unique key `(school_id, id)` in addition to the primary key where it supports same-tenant FK enforcement.
- Child rows carry `school_id` and reference parents using `(school_id, parent_id)`; this prevents a valid ID from another school being attached accidentally.
- Use tenant-first indexes for common access paths, for example `(school_id, academic_year_id, class_id)`, `(school_id, assessment_id, student_id)`, and `(school_id, user_id, status)`.
- Enforce uniqueness at the correct scope: e.g. `(school_id, learner_code)`, `(school_id, teacher_code)`, `(school_id, academic_year_name)`, and `(school_id, subject_code)` unless a reviewed global catalogue is intentionally used.
- Keep role, status, and workflow transitions constrained by service logic plus database constraints. Validate all transitions in a transaction with row locks where concurrent approval/marking could race.
- Avoid cascading deletes for academic history, users, marks, and audit records. Prefer deactivation/soft deletion and explicit retention workflows. Use cascade only for disposable join rows whose lifecycle is strictly owned by the parent.

## 6. Authentication and transaction boundaries

Registration creates a user, credential (when password-based), membership/invitation state, and audit event atomically. Login verifies a password hash with a supported library, checks user and membership status, then issues a short-lived access token and rotates a high-entropy refresh credential stored only as a hash. Reset completion consumes a single-use token, changes the credential, revokes active sessions, and writes an audit event in one transaction.

Sensitive writes must be transactional: mark save + audit; mark submission + state transition + notifications/outbox; exam answer save + attempt state; invitation acceptance + membership creation; and account linking + audit. Deliver email/SMS/WebSocket events after commit using an outbox/worker so a failed provider does not roll back academic records.

## 7. Constraints before executable DDL

This document is logical guidance, not a ready-to-run schema. Before authoring migrations, confirm the live MySQL server/version, source drift, target ID representation, exact RMS table inventory, data volume, values violating proposed constraints, uniqueness/duplicate cases, and application query contracts. Build and test the DDL against isolated staging data before any production change.
